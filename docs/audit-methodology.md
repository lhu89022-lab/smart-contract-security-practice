# 智能合约审计方法论

> 这份文档记录我在审计 4 个靶场合约过程中总结出的**可复用流程**。
> 核心结论：**快不是「看得快」，是知道先看哪里。**

---

## 1. 核心原则：用搜索，不用阅读

**90% 的严重漏洞集中在 10 个模式里。**

一个几千行的合约，如果从头到尾逐行读，你会在大量的 getter、事件、参数校验上耗光注意力，而真正要命的那两三行藏在中间。

**正确做法是：先用 `Ctrl+F` 把可疑的行全部捞出来，再对这几行逐字推演。**

---

## 2. 十一个搜索关键词

拿到一份陌生合约，按顺序搜这 11 个词：

| # | 关键词 | 要问的问题 | 关联漏洞 |
|---|---|---|---|
| 1 | `.call{value:` | **改账行在它上面还是下面？** | 重入 |
| 2 | `.transfer(` / `.send(` | 同上（`transfer` 只给 2300 gas，但仍然是外部调用） | 重入 |
| 3 | `tx.origin` | **有就是洞，没有例外** | 钓鱼 |
| 4 | `require(` | 查的是**人**、**钱**、还是**状态**？ | 访问控制缺失 |
| 5 | `public` / `external` | 每一个都问：**谁能按这个按钮？** | 权限 |
| 6 | `delegatecall` | 存储布局对得上吗？ | 存储冲突 |
| 7 | `block.timestamp` / `prevrandao` / `blockhash` | 被当作随机数用了吗？ | 随机数可预测 |
| 8 | `selfdestruct` | 谁有权销毁？ | 强制转账 / 逻辑破坏 |
| 9 | `unchecked` | 里面的算术会溢出吗？ | 整数溢出 |
| 10 | `assembly` | 逐行看，没有捷径 | 各种 |
| 11 | `onlyOwner` | **真的加在需要它的函数上了吗？** | 权限漏加 |

---

## 3. 六十秒扫描清单

时间紧的时候按这个顺序过一遍：

```
① 搜 .call{value: / .transfer( / .send(
   → 找到每一处转账，和它对应的改账行比位置
   → 转账在上 = 重入

② 搜 tx.origin
   → 出现即为漏洞

③ 搜 public / external
   → 每个函数问「谁能按」
   → 重点看：能碰钱的函数有没有身份检查

④ 搜 require(
   → 每个条件分类：人 / 钱 / 状态
   → 缺失的类别 = 缺失的保护

⑤ 写下不变量，找破坏它的路径
   → 合约余额 == Σ 用户余额 + 手续费池？
```

## 4. 函数三分类

**新手最大的时间浪费，是在 getter 上花了和 `withdraw()` 一样多的时间。**

| 分类 | 特征 | 处理方式 |
|---|---|---|
| 🔴 **碰钱的** | 含 `msg.value`、`.call{value:`、`.transfer(`、`address(this).balance`、金额相关的 `mapping` 写入 | **逐行读，逐行推演** |
| 🟡 **改状态的** | 修改 `mapping`、`uint` 状态变量，但不涉及转账 | 细读，检查与其他函数的交互 |
| ⚪ **纯读的** | `view` / `pure` / 自动生成的 getter | **扫一眼跳过** |

**真实审计的时间分配大致是：**

```
15%  通读一遍，建立全局图景
60%  在少数几个热点函数上来回推演
25%  写 PoC 验证
```

> **「快」的意思是：快速扔掉 80% 的代码。**

---

## 5. 六问法

拿到**任何一个函数**，按顺序问这 6 个问题。**关键是逐个函数问，不是整篇看一眼。**

| # | 问题 | 对应漏洞 |
|---|---|---|
| 1 | **谁能按这个按钮？有没有 `require` 检查身份？** | 访问控制缺失 |
| 2 | **它先改账，还是先转账？** | 重入 |
| 3 | **它把钱转给谁？金额算得对吗？** | 逻辑错误 / 越权 |
| 4 | **检查身份用的是 `msg.sender` 还是 `tx.origin`？** | 钓鱼 |
| 5 | **转账失败会怎样？会不会拖垮所有人？** | 拒绝服务 |
| 6 | **有没有用「随机」？** | 随机数可预测 |

**回答「没有」也是结果** —— 干净函数的六问答案全是「无」，这同样是审计结论。

## 6. 三类行：读 / 检查 / 改账

这是最容易混淆、也是我在审计 [Escrow](../audit-reports/Escrow.md#es-01-转账前没有扣减余额可无限重复领取) 时踩过的坑。

| 类型 | 长什么样 | 会改变状态吗 |
|---|---|---|
| **读** | `uint amount = balances[msg.sender];` | ❌ 只是把数字抄到纸上 |
| **检查** | `require(amount <= balances[msg.sender]);` | ❌ 只是拦住，什么都不改 |
| **改账** | `balances[msg.sender] = balances[msg.sender] - amount;` | ✅ **真的改了** |

> **判断标准只有一条：看那个 `mapping` 在等号的哪一边。**
>
> - 在等号**左边** → 改账
> - 在等号**右边** → 只是在看

**`balances` 出现在 `<=` 的右边、`+` 的右边，都不是改账。**

**只有第三种会改变世界，前两种什么都不改变。**

> 缺失「改账行」是一个完整的漏洞类别 —— 它不需要攻击合约，手点就能无限取款。

---

## 7. `require` 三分类：人 / 钱 / 状态

**看到 `require` 不等于「这里有人管着」。**

`require` 里的条件只可能属于三类：

| 类型 | 例子 | 管住了什么 |
|---|---|---|
| **人** | `msg.sender == owner`、`hasRole(...)` | 谁能调用 |
| **钱** | `amount <= x`、`msg.value >= 1 ether` | 数额是否合法 |
| **状态** | `amount > 0`、`pot >= 3 ether`、`!paused` | 当前是否允许 |

> **`require` 本身不是保护，它只是一个条件。**
> **你得看它里面的条件，是不是管住了该管的那样东西。**

**典型误判：**

```solidity
require(amount <= totalDeposits / 10, "fee too high");
payable(msg.sender).transfer(amount);
```

这一行看起来「有检查」，但它检查的是**金额**，**一个字都没提「人」** —— 任何人都能调用，而且因为函数从不修改 `totalDeposits`，可以**反复调用直到合约归零**。

> 比喻：`require` 是一把锁。**锁装在门上才有用** —— 装在窗框上（`tx.origin`）、装在「金额」上（而不是「人」上），都等于没装。

## 8. 三个必须检查的不变量

**最高级的一招不是读代码，是写下一个等式，然后问「什么情况下它不成立」。**

| # | 不变量 | 被破坏意味着 |
|---|---|---|
| 1 | `合约余额 ≥ Σ 所有用户余额之和` | **坏账** —— 最后一个取款的人取不出钱 |
| 2 | `只有本人能动本人的钱` | 越权 / 访问控制缺失 |
| 3 | `总账 == 各分账之和` | 会计不一致 |

**任何能让这三条不成立的路径，就是漏洞。**

实例（摘自 [`contracts/Bank.sol`](../contracts/Bank.sol)）：

```
address(this).balance == Σ balances[user] + fees
```

```
存入 1 ether  → balances[你] = 0.99,  fees = 0.01  →  1 == 0.99 + 0.01  ✓
取出 0.99     → balances[你] = 0,     fees = 0.01  →  0.01 == 0 + 0.01  ✓
collectFee    → balances = 0,         fees = 0     →  0 == 0 + 0        ✓
```

## 9. 漏洞不是「代码写错了」，是「某个假设被打破了」

把这句话当成审计的元规则。逐个检查代码隐含的假设：

| 代码假设了什么 | 要问的问题 |
|---|---|
| 「用户只能取自己的钱」 | 什么情况下能取到**别人**的钱？ |
| 「余额够转」 | 什么情况下**不够**，但代码以为够？ |
| 「owner 是好人」 | owner 能不能作恶？（即使代码没错 —— 这叫**中心化风险**） |
| 「外部调用会成功」 | 失败了会卡住**所有人**吗？ |
| 「这两个变量同步」 | 什么操作**只改了其中一个**？ |
| 「这个值不会变」 | 什么操作能改它？改了之后下游怎么办？ |
| 「只有我能调这个函数」 | 检查是不是装错了地方（`tx.origin` / 查金额而非查人）？ |

## 10. 误报清单：把「看起来危险」和「实际危险」分开

**误报的代价比漏报更高。** 公开赏金平台有信誉分机制，报一堆 invalid 会掉分，严重时被限制提交。

### 重入的两个前提，缺一不可

1. **函数里真的发生了外部调用** —— 有 `.call{value:` / `.transfer(` / `.send(`
2. **转账行在改账行之前**

**只要第 1 条不成立，就不可能重入** —— 无论这个函数改了多少份状态、看起来多可疑。

### 两个高频误报来源

| 误报来源 | 真相 |
|---|---|
| 「看到了 `require`，所以这里有人管着」 | `require` 可能查的是**金额**或**状态**，跟「人」无关 |
| 「改了多份状态 / 看到 `.call{value:`，所以一定是重入」 | 要确认外部调用**真的发生了**，且**顺序确实反了** |

## 11. 审计报告应该写成什么样

一份好的 finding 包含六件事：

1. **标题** —— 一句话说清「什么问题 + 什么后果」
2. **位置** —— 函数名 + 行号（能直接跳过去）
3. **描述** —— 代码为什么错，用「三类行」拆开
4. **攻击路径** —— 具体步骤，最好附 PoC（攻击合约）
5. **影响** —— 攻击者能拿到什么，是不是**不可恢复**
6. **修复** —— 给可直接用的代码，并说明为什么这样修

**严重性判断的经验法则：**

- 能直接拿走资金 → High
- 能让合约**永久不可用**或状态**不可恢复** → 严重性**升一档**
- 需要 owner 配合才能触发 → 降一档（但如果能骗 owner 点击，就不降）
- **代码没错但设计允许 owner 作恶** → 中危「中心化风险」，不是漏洞但必须报

---

## 12. 快速判断的三句口诀

> **① 能变的量，不能当尺子。**
>
> **② 转账行在改账行上面 → 重入。**
>
> **③ `require` 要看它管的是人、是钱、还是状态。**
